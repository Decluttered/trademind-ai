# Customer Service Message Idempotency Design (P2)

> Outbound platform messages sent after human confirmation must succeed **at most once**; client retries or network timeouts must not produce duplicate platform message records.

## `clientMessageId` Constraint

Table `customer_messages`:

| Field | Description |
| --- | --- |
| `client_message_id` | Stable ID generated by the client (UUID recommended) |
| `conversation_id` | Conversation UUID |

PostgreSQL partial unique index (P2 migration):

```sql
CREATE UNIQUE INDEX ux_customer_msg_client_id
 ON customer_messages (conversation_id, client_message_id)
 WHERE client_message_id IS NOT NULL AND client_message_id <> '';
```

Only one message row can be persisted for the same `clientMessageId` within a given conversation.

## API Behavior

`POST /api/v1/customer/conversations/:id/send-platform-message`

Request body (excerpt):

```json
{
  "reply": "Hello, we've checked the shipping status for you...",
  "suggestionId": "…",
  "idempotencyKey": "optional-legacy",
  "clientMessageId": "client-uuid-001"
}
```

Processing order (`customerchat/send_platform.go`):

1. Validate that `reply` is non-empty.
2. If `clientMessageId` is empty, **fall back** to `idempotencyKey` (for backward compatibility with legacy clients).
3. If `(conversation_id, client_message_id)` already exists → **return the existing row directly**, without calling the platform API again.
4. Otherwise call `platform.CustomerMessage.SendMessage`; on success, write the message and update the conversation's `last_message_at` within a transaction.

## Relationship to the Unified Idempotency Key

Clients are recommended to always pass `clientMessageId`; the server-side idempotency key pattern is:

```text
idempotency.CustomerSend(conversationId, clientMessageId)
→ customer-send:{conversationId}:{clientMessageId}
```

`idempotency.Service.Acquire` could be integrated in the future to close the narrow window where "the platform API succeeded but the DB write failed"; currently the primary path relies on the DB unique index plus a pre-send lookup.

## Platform-Side Idempotency

Provider requests carry:

- TikTok: `idempotency_key` body field
- Shopee / Lazada / Amazon: local `idempotencyLocal` metadata or a template-level key

The platform key should align with or be derived from `clientMessageId` to avoid duplicate sends at the platform level.

## Failure Scenarios

| Scenario | Behavior |
| --- | --- |
| Platform API failure | No write to `customer_messages`; recorded in `customer_failure_events` |
| DB unique conflict (concurrent double write) | One side succeeds; the other should read back the existing row (requires the client to retry with GET or repeat the POST) |
| No `clientMessageId` | Still protected by the unique constraint via `idempotencyKey` alone (if non-empty) |

## Frontend and Acceptance Criteria

Before sending, generate an ID with `crypto.randomUUID()` and fix it to that click; retries reuse the same ID. A second POST with the same `clientMessageId` returns the same message row.
